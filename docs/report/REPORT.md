# A.X K2를 H100 없이 Azure A100 16장으로 서빙하기 — 기술 보고서

작성: Microsoft Korea · 기준일 2026-10 · 정정 2026-11-09 · 대상 모델 [skt/A.X-K2](https://huggingface.co/skt/A.X-K2)

2026-11-09 검토 결과와 이 보고서에서 정정한 내용은 [검토 보고서](REVIEW_2026-11-09.md)에 있습니다. 2026-11-10에 A100에서 가능한 서빙 배치를 모두 실행한 결과는 [스크리닝 보고서](SCREENING_2026-11-10.md)에 있습니다.

## 1. 요약

- **결론.** SKT A.X K2(총 688B, 활성 33B, FP8, MoE, DeepSeek Sparse Attention)를 **H100/B200 없이**
  Azure의 **Standard_ND96amsr_A100_v4 2대(A100 80GB × 16)** 에서 원본 가중치 그대로 서빙했습니다.
  OpenAI 호환 API 하나로 채팅·추론(thinking)·툴 호출·25만 토큰 문맥까지 동작합니다.
- **핵심 난제는 세 가지였습니다.** ① 한 대(8장)에 FP8 가중치 694 GB가 안 들어감,
  ② A100에는 FP8 텐서 코어가 없음, ③ 모델의 희소 어텐션(DSA) 커널이 H100/B200 전용.
- **해결.** ① 두 노드를 vLLM 하나로 묶어 **노드 안은 텐서 병렬(TP8), 노드 사이는 파이프라인 병렬(PP2)**,
  노드 간 통신은 InfiniBand. ② FP8 가중치를 커널 안에서 BF16으로 풀어 계산하는 **Marlin W8A16** 커널.
  ③ 업스트림 vLLM의 미병합 PR #38476(**Triton DSA 커널**)을 SKT vLLM 포크에 이식하고,
  A100에서만 나는 버그 1건(MLA 프리필 dtype)을 2줄로 수정.
- **검증.** 툴 호출 9/9, SKT 자체 니들 테스트 9/9(최대 252,728 토큰), 노드 간 InfiniBand 20.6 GB/s.
- **속도.** 영국 남부 InfiniBand 재측정(2026-10-21, 출력 1,024 토큰, 조건당 1회)에서 단일 사용자 47.5 tok/s,
  동시 32명 합계 404 tok/s(1K 입력)입니다. 같은 측정을 SKT 기술보고서 Fig. 7 조건(동시 32, 입력+출력 총 처리량)으로
  환산하면 **B200 1노드의 0.43배(1K 입력)와 0.39배(8K 입력)** 수준입니다(GPU 16장 vs 8장).
  이전 판의 동시 128명 812 tok/s와 Fig. 7 조건 0.43–0.51배(1K–8K)는 앞 측정 지점의 프롬프트를 캐시에서
  재사용해 부푼 값이 섞여 있어, 재측정 전까지 사용하지 않습니다(5장).
  운영 MAF 챗봇의 짧은 응답 동시성 실측은 별도 조건이며 9.1절에 기록합니다.
- **비용.** 2노드 시간당 약 $82(종량제) / 약 $26(Spot, 영국 남부 소매가). Azure ML 저우선 클러스터는
  2026-03-31부터 Spot으로 할당·과금되므로 이전 저우선 단가($8.19/노드·시간)는 적용되지 않습니다.
- **데모.** ChatGPT 스타일 웹 챗봇이 실제 2노드 클러스터에 연결되어 있습니다(9장).

## 2. 과제와 제약

| 항목 | 내용 |
|---|---|
| 모델 | A.X K2: 61층, MoE(라우팅 전문가) + MLA 어텐션 + DSA(쿼리마다 상위 2,048개 키만 보는 희소 어텐션), FP8 블록 양자화 체크포인트 694 GB, 최대 문맥 262,144 |
| SKT 기준 환경 | B300/B200 한 노드(4–8장), `vllm serve --tensor-parallel-size 8` |
| 우리 조건 | H100/H200/B200 확보 불가. 더 작은/구형 GPU 여러 대로, 고객이 쓰는 Azure 구독 안에서 |
| 구독 제약 | A100 VM 쿼터 0, Spot 쿼터 지역당 100 vCPU, 스토리지 공용 접근 차단 정책 |

## 3. 한계점 — 무엇이 막혔나

| # | 한계 | 왜 문제인가 |
|---|---|---|
| L1 | **메모리**: FP8 가중치 694 GB > A100 8장 640 GB | 한 노드에 모델이 안 올라감. 여러 노드를 "하나의 모델"로 묶어야 함 |
| L2 | **FP8 연산 불가**: A100(SM80)에는 FP8 텐서 코어가 없음 | 기준 환경의 FP8×FP8 행렬곱(W8A8) 커널이 동작하지 않음 |
| L3 | **DSA 커널 부재**: 인덱서(DeepGEMM FP8 MQA logits)와 희소 MLA(FlashMLA sparse)가 SM90/SM100 전용 | 모델 고유의 희소 어텐션을 A100에서 계산할 방법이 없음 |
| L4 | **A100 전용 버그**: MLA 청크 프리필에서 Marlin이 재배치한 int32 가중치 dtype으로 활성값을 캐스팅 | 긴 프롬프트·프리픽스 캐시 적중 시 서버가 죽음(업스트림 v0.23.0에도 존재) |
| L5 | **노드 간 통신**: 기본 설정은 TCP(0.35 GB/s) | 프리필 시 단계 간 은닉 상태 전송이 느림, 노드 걸친 TP는 불가능한 수준 |
| L6 | **GPU 확보**: A100 VM 쿼터 0, 증설 요청 지연 | VM으로는 노드 하나도 못 띄움 |
| L7 | **툴 호출**: 모델 카드 명령만으로는 `tool_choice: auto` 결과가 본문 텍스트로 나옴 | 에이전트/함수 호출 시나리오가 깨짐 (A100과 무관, 기준 명령에도 해당) |

## 4. 해결 — 어떤 연산을 무엇으로 바꿨나

| 한계 | 바꾼 것 | 어떻게 | 결과 |
|---|---|---|---|
| L1 메모리 | 단일 노드 → **2노드 TP8 × PP2** | vLLM `--tensor-parallel-size 8 --pipeline-parallel-size 2 --distributed-executor-backend ray`. 노드 0: 0–30층, 노드 1: 31–60층 + LM 헤드. GPU당 약 42 GiB 가중치(native, 42.2–42.3 GiB), 나머지는 KV 캐시 | 전체 61층 로드·서빙, KV 캐시 673,792 토큰 |
| L2 FP8 연산 | FP8×FP8 행렬곱(W8A8) → **Marlin W8A16** | FP8 가중치는 메모리에 그대로 두고 커널 안에서 BF16으로 풀어 BF16 활성값과 곱함(선형층·MoE 전문가 모두) | 가중치 메모리는 동일. 디코드는 가중치 읽기가 병목이라 영향이 작고, 프리필은 느려짐 |
| L3 DSA | DeepGEMM 인덱서 + FlashMLA sparse → **Triton 인덱서 + Triton 희소 MLA** | vLLM PR #38476을 SKT 포크(v0.23)에 이식. 충돌 1건 수동 병합, H100/B200은 기존 커널을 쓰도록 가드 추가. 파일별 해시로 검증하는 오버레이(`aml/src/dsa_port.json`) | 체크포인트·설정 **무수정**. 모든 층이 B300과 같은 규칙으로 쿼리당 상위 2,048 키 선택. 25만 토큰 니들 9/9 |
| L4 버그 | dtype 캐스팅 조건 | 가중치가 부동소수점 타입일 때만 캐스팅하도록 2곳 수정(앵커 1회 등장 확인 후 패치) | 긴 프롬프트·캐시 적중에서 안정 |
| L5 통신 | TCP → **InfiniBand + GPUDirect RDMA** | 컨테이너에 노출된 200 Gb/s HCA 8개 사용, Azure NDv4 토폴로지 파일 적용, 시작 시 NCCL 프로브로 IB 확인 후에만 사용 | 20.6 GB/s(약 59배), 왕복 454 → 122 µs, 8K 청크 단계 전송 0.67 s → 11 ms(측정 대역폭으로 계산한 값) |
| L6 확보 | VM → **Azure ML 저우선(low priority) 클러스터** | 지역당 300 vCPU, 패밀리 제한 없음 → ND96amsr 3대까지. 실험 작업은 12개 지역, 데모는 3개 지역(uksouth·italynorth·francecentral)에 동시 제출하고 먼저 2노드를 받은 곳만 남김 | 쿼터 증설 없이 확보. 단, 회수(preemption) 가능. 2026-03-31부터 Spot으로 할당·과금 |
| L7 툴 | 파서 설정 | `--tool-call-parser hermes --enable-auto-tool-choice` | 9/9 정답(한국어 호출, 병렬 호출, thinking+호출, 스트리밍, named, required 등) |

### 병렬 구성 한눈에 보기

```mermaid
flowchart LR
  C[클라이언트<br/>OpenAI API] --> A[vllm serve<br/>노드 0]
  subgraph job[Azure ML 작업 · ND96amsr_A100_v4 × 2 · 한 지역]
    subgraph n0[노드 0 · Ray head]
      A --> S0[파이프라인 1단계: 0–30층<br/>TP8 · NVLink · GPU 0–7]
    end
    subgraph n1[노드 1 · Ray worker]
      S1[파이프라인 2단계: 31–60층 + LM 헤드<br/>TP8 · NVLink · GPU 0–7]
    end
    S0 -- 은닉 상태 · NCCL over InfiniBand --> S1
  end
```

**"앞뒤로 나누면 순차 처리 아닌가?"** 한 요청만 보면 그렇습니다. 토큰 하나를 만들 때 1단계(0–30층)를 지나
2단계(31–60층)로 갑니다. 하지만 ① 각 단계 **안에서는** 8장이 한 층의 행렬을 나눠 동시에 계산하고(텐서 병렬),
② 여러 요청이 있을 때는 1단계가 다음 묶음을 처리하는 동안 2단계가 이전 묶음을 처리합니다(파이프라인 병렬).
그래서 동시 사용자가 늘수록 합계 처리량이 올라갑니다(2026-10-21, 1K 입력: 1명 47.5 → 32명 404 tok/s).
노드를 나누는 근본 이유는 속도가 아니라 **메모리**(L1)이고, 노드 사이에 오가는 것은 층 경계의 작은 은닉 상태뿐이라
노드 간 대역폭 요구가 작습니다. 노드 전체를 하나의 TP16으로 묶는 구성도 시험했습니다.
native 측정(2026-10-21)에서 TP16은 한 요청 출력이 기준의 0.77–0.82배로 느렸고, 동시 32명에서는 1K·8K 입력 1.04배,
32K 입력 0.89배였습니다. KV 캐시는 기준의 0.46배라 긴 문맥에 불리합니다.
이전 판의 "짧은 입력에서 12–41% 빠름"은 다른 작업(2026-10-03)의 dense 모드 동시 32명 총 처리량이고,
프리픽스 캐시 재사용이 섞여 재측정 전까지 사용하지 않습니다.

### 기준 환경과 달라진 점

### 속도

GPU 엔드포인트에 직접 실행한 `vllm bench serve`, 랜덤 프롬프트, 출력 256 토큰.
2026-10-03 이탈리아 북부 작업이며 노드 간 연결은 TCP(InfiniBand 끔), max_model_len 65,536, step당 batched token 2,048,
조건당 1회입니다. 1절과 아래 병렬 구성 비교의 2026-10-21 값(영국 남부, InfiniBand, 출력 1,024 토큰)과 조건이 다릅니다.
App Service·MAF·역방향 WebSocket·사용자 HTTP 경로를 포함하는 운영 챗봇 수치가 아닙니다.

| 시나리오 | 출력 tok/s | TTFT 중앙값 | 토큰당 시간(TPOT) |
|---|---:|---:|---:|
| 1명, 1K 입력 | 49 | 355 ms | 19.2 ms |
| 1명, 8K 입력 | 38† | 1.65 s† | 20.0 ms |
| 1명, 32K 입력 | 20† | 7.21 s† | 21.1 ms |
| 동시 32명, 1K 입력 | 360† | 1.83 s† | 76.7 ms† |
| 동시 128명, 1K 입력 | 812† | 2.94 s† | 145.5 ms† |

†: 이 작업은 모든 측정 지점에 같은 난수 시드를 썼습니다. 그래서 뒤 지점이 앞 지점과 같은 프롬프트로 시작해
프리픽스 캐시를 재사용했습니다. 그래서 처리량은 높게, 첫 토큰 시간과 동시 요청의 TPOT는 짧게 나왔습니다. † 값은 재측정 전까지 사용하지 않습니다.
한 요청의 토큰당 시간(TPOT)은 디코드만 재므로 영향을 받지 않습니다.

토큰당 디코드 시간은 1K→32K 문맥에서 19.2 → 21.1 ms로 10% 늘었습니다. 같은 작업의 dense 모드는 15.8 → 19.1 ms로
모든 길이에서 더 짧았습니다. 원인은 프로파일링하지 않았습니다.

  2026-10-21 값으로 환산하면 B200 대비 1K 0.43배, 8K 0.39배, 32K 0.25배입니다(8K 출력 269 → 208 tok/s).

  A100에 FP8 텐서 코어가 없는 것(L2)이 원인으로 보이나, 프로파일링으로 확인하지 않았습니다.
- 16K 이상: 격차가 커집니다. ① MLA KV 캐시가 TP 랭크마다 복제되어 16장 합계 673,792 토큰만 담김
  (32K 입력은 32건 중 20건만 동시 처리), ② DSA 인덱서가 FP8 대신 BF16 Triton으로 돌고, 인덱서 계산량이 입력 길이의
  제곱에 비례(소스 분석, 프로파일링하지 않음).

### 4비트(NVFP4) 한 노드 옵션

SKT의 `skt/A.X-K2-NVFP4`(398 GB)는 **A100 8장 한 노드**에 들어갑니다. vLLM의 능력 검사(SM89 이상 요구)가
하드웨어 제약이 아니라 소프트웨어 검사라는 것을 확인하고 업스트림 변경 2건을 백포트했습니다.
라우팅 전문가는 W4A16으로 돕니다. 같은 날(2026-10-21) 측정에서 NVFP4 8장은 FP8 16장의 0.83–1.10배였습니다
(1K·8K 한 요청 1.01–1.02배, 32K 한 요청 0.86배). 두 구성은 서로 다른 작업·할당에서 측정했습니다. 이 범위에는 KV 용량에
막힌 동시 32의 8K·32K 지점이 포함되고, NVFP4는 GPU 메모리 0.92·최대 시퀀스 128(FP8은 0.90·64)로 실행했습니다.
이전 판의 "동시 32명까지 FP8 2노드와 같은 속도"(1K 입력 1.01–1.06배)는 서로 다른 날짜·지역·연결
(NVFP4 2026-10-04 영국 남부, FP8 2026-10-03 이탈리아 북부·TCP)의 교차 비교이고, 두 작업 모두 같은 시드로
캐시 재사용이 섞여 재측정 전까지 사용하지 않습니다. GPU 수는 절반입니다.
품질은 기능·툴·니들 테스트로만 확인했으므로 고객 데이터로 평가 후 선택을 권합니다.

아래 GPU당 그림은 서로 다른 작업(FP8 2026-10-03, NVFP4 2026-10-04)과 B200 공개값을 맞댄 것입니다.
두 작업 모두 모든 측정점에 같은 시드를 써서 처리량이 높게 나왔습니다(FP8 4K·8K는 위 † 값). 같은 날(2026-10-21)
D 기준으로 1K는 B200 노드의 0.47배(889.8/1,900)입니다. B200 NVFP4의 GPU 수(4장)는 공개 그림에 표시되지 않은 가정입니다.

### 추가 실험: 병렬 구성 7개 비교 (2026-10-21, 영국 남부)

FP8 5구성(노드 2대, 노드 간 InfiniBand)과 NVFP4 2구성(단일 노드)을 같은 날 같은 방식으로 측정했습니다.
FP8과 NVFP4는 서로 다른 작업·할당입니다. 측정 지점마다 다른 시드를 써서 캐시 재사용은 없었습니다.
배수는 기준 구성(FP8은 A, NVFP4는 D) 대비 출력 tok/s이고, 입력 1K / 8K / 32K 순입니다. 조건마다 1회 측정입니다.

| 구성 | GPU | KV 토큰 | 1명 출력 | 동시 32명 출력 |
|---|---:|---:|---|---|
| A TP8×PP2 (기준) | 16 | 673,792 | 47.5 / 41.9 / 31.9 tok/s | 404 / 208 / 61 tok/s |
| B0 TP16 | 16 | 310,080 | ×0.79 / 0.82 / 0.77 | ×1.04 / 1.04 / 0.89 |
| B TP16+EP16 | 16 | 309,376 | ×0.70 / 0.72 / 0.70 | ×0.98 / 0.98 / 0.83 |
| C1 TP8×PP2+EP8 | 16 | 673,216 | ×0.88 / 0.89 / 0.91 | ×0.92 / 0.92 / 0.92 |
| C2 DP2×TP8+EP16 | 16 | 238,720 + 238,656 | ×0.50 / 0.54 / 0.56 | ×1.12 / 1.36 / 1.18 |
| D NVFP4 TP8 (기준) | 8 | 254,016 | 48.3 / 42.4 / 27.3 tok/s | 445 / 188 / 51 tok/s |
| E NVFP4 TP8+EP8 | 8 | 253,120 | ×0.93 / 0.93 / 0.93 | ×0.95 / 0.93 / 0.94 |

- **EP만 켜서 빨라진 경우는 없었습니다.** EP를 켜고 끈 3쌍(B·B0, C1·A, E·D)을 각각 1회 측정했습니다.
  EP를 켜면 한 요청 TPOT가 8–14% 늘었고, 출력 tok/s는 한 요청에서 7–12%, 동시 32명에서 5–8% 줄었습니다.
  18개 비교가 모두 1 미만이지만 독립 표본은 3쌍뿐입니다. 원인은 그룹 라우팅(8그룹 중 4그룹 선택)과
  linear 전문가 배치가 겹친 부하 불균형으로 추정합니다. round-robin 배치는 시험하지 않았습니다.
- **한 요청은 FP8 구성 중 TP8×PP2(A)가 가장 빠릅니다.** NVFP4 TP8(D, GPU 8장, 같은 날 별도 작업)은
  1K·8K에서 A의 1.02·1.01배, 32K에서 0.86배입니다.
- **동시 32명에서 세 입력 모두 기준보다 빠른 구성은 DP2×TP8+EP16(C2)뿐입니다**(×1.12~1.36).
  TP16(B0)은 1K·8K에서 ×1.04, 32K에서 ×0.89입니다. 5% 이하 차이는 1회 측정으로 구별하지 않습니다.
  C2는 한 요청에서 약 절반 속도입니다. C2와 A의 비교에는 API 서버 2개, 엔진 2개라 배치 한도 합계 2배, 컨텍스트 차이가 섞였습니다.
- 같은 기준 구성(A)의 8K·동시 32명 출력이 2026-10-03(269 tok/s)과 2026-10-21(208 tok/s) 사이에 23% 달랐습니다.
  주원인은 2026-10-03 측정의 프리픽스 캐시 재사용입니다(두 측정 사이에는 priority 스케줄링 등 설정 차이도 있습니다).
  디코드 지표(한 요청 TPOT·ITL)는 캐시 재사용의 영향을 받지 않고, A·D를 다른 날 다시 띄워도 0.9% 안에서 재현됐습니다.
- 7구성 모두 기능 4/4, 툴 호출 9/9를 통과했고 CUDA graph로 시작했습니다. 기능 점검이며 품질 동등성의 근거는 아닙니다.

## 8. 한계와 운영 권고

- **용량.** 저우선/Spot은 회수될 수 있고 확보도 불안정했습니다(12개 지역 중 2곳에서만 2노드 확보).
  운영 환경은 고객 구독의 **종량제 또는 예약 인스턴스**로, 같은 이미지·명령을 AKS(KubeRay/LeaderWorkerSet)나
  CycleCloud Slurm에서 실행하는 것을 권합니다.
- **미병합 업스트림 코드.** 희소 어텐션은 vLLM PR #38476(작성자 표현 "concept") 이식에 의존합니다.
  vLLM 버전을 올릴 때마다 커널 테스트·2층 비교를 다시 돌리고, 업스트림 지원이 들어오면 교체하세요.
  2026-11-09 검토에서 이 포트의 인덱서 디코드 커널에 잠재 버그 1건을 소스 분석으로 찾았습니다. 행 너비가 64의 배수가
  아닌 단계에서 다음 요청의 앞쪽 토큰 최대 63개의 점수를 덮어쓰고, 텐서 끝을 넘겨 쓸 수 있습니다. 수정은 포트
  (`aml/src/dsa_port.json`)에 넣었고 CPU에서만 확인했습니다. GPU 회귀 시험은 아직 하지 않았습니다. 이 보고서의 결과는 모두
  수정 전 커널로 얻었고, 버그가 결과에 준 영향은 확인하지 않았습니다(처리량, 기능·툴 점검에서는 드러나지 않았습니다).
- **긴 입력 동시성.** 16장 KV 673,792 토큰 → 32K 입력 20건, 64K 10건, 120K 5건이 동시 한계.
  더 필요하면 2노드 그룹을 복제(데이터 병렬)합니다.
- **아주 긴 입력과 대화형 지연.** 25만 토큰급 입력의 prefill이 도는 동안 스케줄 단계 하나가 수 초로 늘어,
  같은 클러스터의 다른 대화도 그만큼 느려집니다(운영 중 관찰이며 증거 파일은 없습니다: NIAH 평가 중 클러스터 전체 생성 약 40 tok/s,
  채팅 첫 토큰 1분 이상. 일반 평가 중에는 약 400 tok/s, 세 문장 답변 약 8초). 긴 문서 처리와 대화형 트래픽은 그룹을 나눠 받는 것을 권합니다.
- **기동 시간.** GPU를 켜서 첫 응답까지 약 25분입니다(데모 운영 기록). 측정 기록으로는 가중치 694 GB 다운로드가
  노드당 약 7–15분(작업 4개, 403–926초), native TP8×PP2 서버 시작이 약 4–5분(261–302초)입니다. 노드 할당 대기는 별도입니다.
  상시 서비스라면 가중치를 노드 로컬 NVMe나 Azure Managed Lustre에 미리 두고 노드를 계속 켜 두세요.
- **알려진 버그.** vLLM 0.23의 `persistent_topk`에는 업스트림 수정 #49139가 없습니다(32K 초과 시퀀스 2개가 짧은 시퀀스를
  사이에 두고 배치될 때). SKT 포크도 동일하며 A100 고유 문제는 아닙니다.
- **재현성.** 비트 단위 재현이 필요하면 FP8 지원 GPU(SM89 이상)가 필요합니다.
- **추측 디코딩(EAGLE3) 이득 미확인.** TP8×PP2에서는 쓸 수 없고, TP16에서는 eager로만 돌아 이득을 확인하지 못했습니다(5장 추가 실험). 속도는 B200 대비 위 수치 수준입니다.
- **품질 평가 범위.** 6장의 공개 벤치마크와 니들·툴 테스트는 전체 품질 평가가 아닙니다. 고객 데이터로 추가 평가를 권합니다.
- **측정 방법.** 구성마다 서버를 1번 띄워 측정했고, 동시 32명 측정은 요청 32개를 한꺼번에 보내는 방식이라 실제 트래픽과 다릅니다.

### 9.1 운영 MAF 챗봇의 제한된 동시성 실측

**실측 시각:** 2026-10-07 07:03:40–07:04:05 UTC (16:03:40–16:04:05 KST).
PDF·도구 금지/재허용·취소의 실제 A.X 검증과 프런트엔드 배포를 마친 뒤,
병합된 `50648d192843db8f68ca922e587d57461b879be0` 릴리스에서만 순서대로 측정했습니다.
GPU는 동일한 UKSouth 2노드/16 A100, TP8×PP2, FP8 native DSA/vLLM이며 작업·가중치·설정을 변경하지 않았습니다.
App Service는 Korea Central B1입니다.

**방법:** 실제 UI와 같은 `POST /api/agent`에 새 `/api/workspace` 토큰을 각각 발급했습니다.
로컬 WSL HTTP 클라이언트에서 워밍업 1건을 제외하고 c1/c2/c4를 각각 2회 실행했습니다
(유효 요청 2/4/8건, 합계 14건). 대화 이력·첨부 없이 다음 고정 요청을 사용했습니다.

```json
{
  "messages": [{
    "role": "user",
    "content": "HTTP 응답의 상태 코드, 헤더, 본문이 각각 어떤 역할인지 한국어로 정확히 세 문장으로 설명해 주세요."

```

권한은 `X-AX-Workspace` 헤더의 새 대화 토큰이며 원시 증거에는 토큰을 저장하지 않았습니다.
서버 기본 temperature 0.6/top_p 0.95를 유지했습니다. GPU/서비스를 한 번 워밍업했지만
HTTPS 연결 풀은 c2/c4 첫 실행에서 확장될 수 있으므로 모든 연결이 사전 워밍업된 조건은 아닙니다.
실제 vLLM 스트림의 `usage`에서
system 메시지 등을 포함한 입력은 요청당 **980토큰**, 출력은 **67–108토큰**이었습니다.
14건 모두 자연 종료(`stop`), 모델 호출 1회, 실제 추론 텍스트·도구 호출 0건이며 출력 상한에 도달하지 않았습니다.
문자 수 기반 추정이나 GPU 직접 벤치마크 값을 대입하지 않았습니다.

TTFT는 HTTP 요청 시작부터 첫 답변 content chunk까지, 전체 응답은 실제 MAF terminal end/SSE 종료까지입니다.
HTTP/TLS·App Service·MAF·역방향 링크·vLLM·네트워크 전송을 포함하지만 토큰 발급과 브라우저 페인트는 제외합니다.
합계 출력 tok/s는 두 실행의 출력 토큰 합계를 두 실행의 batch wall time 합계로 나눈 값입니다.
요청별 전달 decode 속도는 각 요청의 출력 토큰을 첫 content 이후 종료까지의 시간으로 나눈 값으로,
동시 요청 합계 속도나 순수 GPU 커널 속도와 다릅니다.

각 실행 전 Gate active/waiting=0을 확인하고 약 1초 간격으로 상태를 관찰했습니다.
관찰된 프런트엔드 waiting 최댓값은 0이고 SSE queue 이벤트도 없었습니다.
자체 요청 수를 초과하는 활동·대기열 또는 30초/워밍업 3배 이상의 지연이 보이면 자체 토큰만 취소하도록 제한했습니다.
별도 취소 확인 1건은 첫 content 후 실제 `/api/workspace/cancel`로 중단했고,
취소 요청 확인 응답은 15.59ms, terminal state는 `cancelled`, 이후 Gate active/waiting=0이었습니다.
취소된 요청의 최종 usage는 미제공이므로 출력 토큰/속도를 추정하거나 위 14건에 포함하지 않았습니다.

**한계:** 각 수준은 두 번뿐이고 응답 길이도 짧으며 표본별 분량이 다릅니다.

PDF·Web IQ·thinking·장문 이력·긴 출력, 지속 부하와 GPU 내부 스케줄러 대기는 이 측정에 포함하지 않았습니다.
