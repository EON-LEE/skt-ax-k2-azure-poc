# A.X K2 A100 서빙 실험 검토 결과 (2026-11-09)

- 작성일: 2026-11-09
- 대상: 2026-10-21 병렬 구성 7종 비교(영국 남부, InfiniBand), 그 이전 측정(2026-10-02~10-06), 관련 문서와 발표 자료. 검토 기준 커밋은 `ca24165`이다.
- 방법: 검토자 5명이 저장소를 읽기 전용으로 독립 검토했다. Azure와 GPU는 사용하지 않았다.
- 표시
  - **확인**: 소스 코드, 증거 JSON, 계산으로 확인했다.
  - **추정**: 소스 분석과 계산에서 나온 값이다. GPU에서 측정하지 않았다.
  - **미확인**: 기록된 증거로 판단할 수 없다.
  - **계획(미실행)**: 아직 실행하지 않은 계획이다.

구성 이름은 다음과 같다.

| 이름 | 구성 | GPU |
|---|---|---|
| A | FP8 TP8×PP2 (기준, 현재 제안) | 16 |
| B0 | FP8 TP16 | 16 |
| B | FP8 TP16+EP16 | 16 |
| C1 | FP8 TP8×PP2+EP8 | 16 |
| C2 | FP8 DP2×TP8+EP16 | 16 |
| D | NVFP4 TP8 (노드 1대) | 8 |
| E | NVFP4 TP8+EP8 (노드 1대) | 8 |

## 1. 결론

1. **병렬 구성은 의도대로 동작했다(확인).** 7개 구성이 모두 주장한 TP·PP·EP·DP로 실행됐다. GPU별 KV 메모리 계산, 랭크 배치, 전문가 배치, InfiniBand 사용 기록이 서로 일치한다. eager 모드로 떨어진 단계는 없다.
2. **실행된 모델 코드는 맞다(확인). 다만 DSA 포트 코드에 잠재 버그가 1건 있다(소스 분석, GPU 재현 전).** 특정 단계에서 다음 요청의 앞쪽 토큰 최대 63개의 인덱서 점수를 덮어쓰고, 텐서 끝을 넘겨 쓸 수도 있다. 기존 측정의 처리량과 기능·도구 점검에서는 드러나지 않았다. 출력과 속도에 미친 영향은 미확인이다. 수정은 이 보고서와 같은 변경에서 포트에 넣었고 CPU에서만 확인했다. 고객용 재측정 전에 GPU 회귀 시험을 해야 한다.
3. **비교 중 일부만 공정하다.** EP를 켜고 끈 3쌍(B·B0, C1·A, E·D)은 공정하다(확인). C2와 A, FP8과 NVFP4, 입력 32K·동시 32 비교에는 다른 조건이 섞였다.
4. **측정 방법은 고객에게 처리량 순위, 용량, 비용을 주장하기에 부족하다.** 구성마다 서버를 1번만 띄워 측정했다. 동시 32 측정은 요청 32개를 한꺼번에 보내는 방식이라 실제 트래픽과 다르다. 10-03·10-04 측정 일부는 앞 측정 지점의 프롬프트를 프리픽스 캐시에서 재사용했다. 그래서 처리량은 높게, 첫 토큰 시간은 짧게 나왔다(확인).
5. **문서의 숫자는 대부분 맞다. 그러나 주장과 표기에 중대한 오류가 10건 있다(확인).** 예를 들어 "동시 32에서 기준보다 빠른 구성은 C2뿐"은 틀렸다. B0도 1K·8K 입력에서 ×1.04였다. 10건은 이 보고서와 같은 변경에서 고쳤다(10절).
6. **A100에서 시도하지 않은 최적화가 남아 있다.** `--max-model-len` 축소와 EP 전문가 배치 변경(round-robin)은 플래그 하나로 시험할 수 있다. 결과에 따라 현재 결론이 바뀔 수 있다(추정).
7. **다음 단계는 대표 구성 3개를 반복 측정하는 것이다(계획, 미실행).** 지연 기준(SLO)을 지키는 최대 처리량(goodput)과 신뢰구간을 낸다. 최소안 비용은 약 55노드시간, Spot 기준 약 705달러, 종량제 기준 약 2,240달러다(추정). 계획은 8절에 있다.

## 3. 구성별 판정

| 구성 | 의도대로 실행 | 핵심 근거 | 비교 공정성 |
|---|---|---|---|
| A | 확인 | 노드0이 0~30층, 노드1이 31~60층을 맡았다. 각 노드 안에서 TP8이다. KV 673,792토큰 | 기준. 맨 먼저 실행했다 |
| B0 | 확인 | TP 랭크 8이 노드1에 있다. 노드를 걸친 그룹이라 custom all-reduce가 꺼졌다. KV 310,080토큰 | B와 비교는 공정하다. A보다 KV가 0.46배라 32K·동시 32 비교는 용량 비교가 된다 |
| B | 확인 | GPU당 전문가 16개다. EP 랭크 8은 128~143번을 맡았다. DP=1이라 all2all이 없다 | B0와 공정하다 |
| C1 | 확인 | 파이프라인 단계마다 EP8이다. GPU당 전문가 32개 | A와 공정하다 |
| C2 | 확인 | 엔진 2개가 노드마다 1개씩 떴고 둘 다 요청을 처리했다. allgather/reduce-scatter 방식을 썼다 | A와 비교는 조건이 섞였다. API 서버 2개, 엔진 2개라 배치 한도 합계 2배, 컨텍스트 238,656토큰, 공유 전문가 복제, 마지막 실행 |
| D | 확인 | 노드 1대에서 TP8이다. 전문가는 Marlin W4A16으로 실행됐다. KV 254,016토큰 | FP8과 비교는 조건이 섞였다. 다른 작업과 VM, GPU 메모리 0.92(FP8은 0.90), 최대 시퀀스 128(FP8은 64) |
| E | 확인 | GPU당 전문가 32개 | D와 공정하다. 단 D 다음에 1회만 실행했다 |

모든 구성에 공통으로 확인한 사항은 다음과 같다.

- 모든 단계가 CUDA graph를 캡처했다. eager로 재시도한 단계는 없다.
- FP8 단계에서는 모든 워커 프로세스가 InfiniBand(GPUDirect RDMA)를 사용했다. 통신 그룹별 전수 확인은 하지 못했다. 런처가 NCCL 로그를 12줄만 남겼기 때문이다(미확인).
- 서버 시작 시간은 구성의 특성으로 볼 수 없다. 단계마다 1회 측정했고, 앞 단계가 남긴 컴파일·페이지 캐시의 영향을 받는다. 예를 들어 세 번째로 실행한 C1은 151초, D 다음에 실행한 E는 312초였다.

## 4. 실행 코드 검토 결과

### 4.1 모델 코드

- A.X K2 모델 코드의 TP·PP·EP·DP 처리는 upstream DeepSeek-V3.2 구현과 같다(확인).
- MLA 잠재 KV와 DSA 인덱서는 TP 랭크마다 복제된다. 설계상 정상이다. TP16의 KV 용량이 TP8×PP2의 0.46배인 이유가 이것이다. 층·토큰당 1,284바이트(MLA 1,152 + 인덱서 132)로 계산하면 측정된 KV 용량과 0.1% 안에서 일치한다(확인).
- PP2는 61층을 31층과 30층으로 나눈다. 두 단계의 부하 차이는 약 6%다(추정).
- A100에서 실제로 실행되는 fork 변경은 A.X K2 모델 코드뿐이다. fork의 DP 관련 변경(`sync_drafter_run_across_dp`)은 추측 디코딩을 켤 때만 실행된다. 따라서 이번 결과와 관계가 없다(확인).
- Ampere 수정 2줄은 정확하다. native DSA 실행에서는 지나가지 않는 경로이고 dense 모드에서만 쓰인다(확인).

### 4.2 버그: 인덱서 점수 덮어쓰기

- **위치:** DSA 포트(PR #38476, upstream 미병합)의 `vllm/v1/attention/ops/mqa_logits_triton.py` 디코드 커널 저장 부분.
- **내용:** 커널은 점수를 64토큰 블록 단위로 저장한다. 행 너비(배치의 최대 길이)가 64의 배수가 아니면, 가장 긴 행의 마지막 블록이 다음 요청 행의 앞쪽 최대 63칸에 −inf를 쓴다. 그 행이 마지막 행이면 텐서 끝을 최대 252바이트 넘겨 쓴다.
- **발생 조건:** 인덱서가 CUDA graph 없이 실행되는 단계에서만 생긴다. 프리필과 디코드가 섞인 단계가 여기에 해당한다. C2에서는 다른 복제본이 프리필 중인 단계도 해당한다. 디코드만 있는 단계(FULL graph)는 안전하다.
- **영향(추정):**
  - 다음 요청의 앞쪽 토큰이 그 단계의 모든 층에서 DSA top-k(2,048개)에서 빠진다. 그 요청의 컨텍스트가 2,048토큰보다 길 때 생긴다. 빠지는 토큰은 대개 BOS와 시스템 프롬프트다.
  - 텐서 끝을 넘는 쓰기(최대 252바이트)는 컨텍스트 길이와 관계없이 다른 메모리를 손상시킬 수 있다.
  - 기존 측정의 처리량과 기능·도구 점검에서는 드러나지 않았다. 출력과 속도에 미친 영향은 미확인이다.
- **상태:** 소스 분석과 인덱스 계산 에뮬레이션(CPU)으로 찾았다. GPU에서 재현하지 않았다. PR의 테스트는 행 너비가 항상 64의 배수라 이 경우를 잡지 못한다.
- **수정 방향:** 저장 마스크에 `k_offset < width` 조건을 추가한다. 또는 행 너비를 64의 배수로 올린다.
- **수정 반영:** 이 보고서와 같은 변경에서 `aml/src/dsa_port.json`이 이 파일을 여섯 번째 패치 파일로 고친다. 수정한 커널은 저장을 행 너비 안으로 제한한다. CPU의 Triton interpreter로만 확인했다(수정 전 행 밖에 56~112개 값을 썼고, 수정 후 0개, 행 안의 값은 비트 단위로 같다). CUDA 회귀 테스트(`aml/src/bench/test_dsa_port_regression.py`)는 아직 GPU에서 실행하지 않았다. 수정은 이 변경 이후의 실행부터 적용된다. 지금까지 기록한 결과는 모두 수정 전 커널로 실행했고, 버그가 그 결과에 준 영향은 미확인이다.

### 4.4 결과 재해석

- **TP16의 단일 요청 디코드 손해(+24~26%)는 포트 탓이 아니다.** 노드 간 all-reduce가 주원인으로 추정된다. 프로파일로 확인하지 않았다. 단일 엔진이 매 단계 다른 노드의 워커에 스케줄 결과를 보내는 제어 경로 지연도 원인 후보다.
- **EP의 단일 요청 손해(+8~14%)도 포트 탓이 아니다.** 그룹 라우팅과 linear 전문가 배치의 상호작용이 주원인으로 추정된다(A8). 이 추정이 맞으면 "A100에서 EP는 이득이 없다"는 결론은 linear 배치에만 해당한다.
- **C2의 단일 요청 손해(약 2배)에는 두 가지 메커니즘이 있다(소스 확인).** 첫째, 요청이 없는 복제본도 더미 단계를 함께 실행한다. 둘째, MoE 층마다 노드 간 allgather/reduce-scatter를 실행한다. 둘 다 upstream vLLM의 동작이다. 각각의 기여도는 프로파일 전까지 미확인이다.
- **C2의 동시 32 이득(×1.12~1.36)에는 여러 요인이 섞여 있다.** 포트 휴리스틱(A1, A2, 추정), API 서버 2개, 배치 한도 합계 2배(엔진 2개), DP가 복제된 어텐션 작업을 나눈 효과가 함께 작용했다. 기여도는 분리하지 못했다. A가 동시 32에서 PP 마이크로배치로 순방향당 16토큰을 처리하는지도 미확인이다. 그래서 A1·A2가 어느 구성에 유리한지도 확정할 수 없다.

## 5. 측정 방법 검토 결과

### 5.1 문제

| 문제 | 영향 |
|---|---|
| 구성마다 서버를 1번만 띄워 측정했다 | 실행 간 편차를 알 수 없다. 참고로 A와 D는 다른 날 다시 띄운 측정에서 디코드 지표가 0.9% 안에서 재현됐다 |
| 동시 32 측정은 요청 32개를 한꺼번에 2번 보낸다 | 프리필 대기가 측정 시간의 8~14%(1K), 41~50%(8K), 55~71%(32K)를 차지한다(추정). 디코드 속도보다 프리필 처리량을 잰다 |
| 입력 32K·동시 32는 모든 구성의 KV 용량을 1.6~4.3배 넘는다 | 속도가 아니라 KV 용량을 잰다. A와 C1은 선점(preemption)이 불가피했다. 선점 횟수는 기록하지 않았다 |
| 10-03·10-04 측정은 모든 지점에 같은 시드를 썼다 | 뒤 지점이 앞 지점의 프롬프트를 캐시에서 재사용했다. A의 8K·동시 32가 10-03에는 269.4 tok/s였지만, 오염이 없는 10-21 측정은 208.3 tok/s다(−22.7%) |
| 요청 수가 적다 | 단일 요청은 4개, 동시 32는 64개다. P99는 사실상 최댓값이다 |
| 필요한 지표가 없다 | 지연-처리량 곡선, SLO 기준 goodput, 개방형(Poisson) 도착, 실제 텍스트, 정상 상태 구간, 선점·캐시 적중 카운터, 반복 신뢰구간, 장시간 부하, 구성별 출력 동등성 |

### 5.2 지금 고객에게 말할 수 있는 것

다음 내용은 "같은 할당에서 구성마다 1회 실행했다"는 조건을 함께 밝히면 말할 수 있다.

1. 단일 요청 디코드 시간(TPOT) 증가: B0 +24~26%, B +40~44%, C1 +12~14%, C2 +88~100%. E는 D보다 +8%.
2. 구성별 KV 용량과, 입력 32K·출력 1K 요청을 선점 없이 동시에 담을 수 있는 수: A·C1 19개, B·B0 9개, C2 14개(엔진당 7개), D·E 7개. A·C1은 측정 중 20개까지 받았다. 이때 선점이 불가피했다고 계산된다(선점 횟수는 기록되지 않았다).
3. C2의 단일 요청 속도는 A의 약 절반이고, 최대 컨텍스트는 238,656토큰이다.
4. 32K 입력의 첫 토큰 시간은 PP2 구성(A 8.9초, C1 9.3초)이 나머지 구성(12.7~15.5초)보다 짧다.
5. 모든 구성이 기능 점검 4/4, 도구 호출 9/9를 통과했다. 이는 기능 점검이며 품질 동등성의 증거가 아니다.

### 5.3 재측정 전까지 말하면 안 되는 것

- 처리량 순위. 예: "동시 요청이 많으면 C2가 가장 빠르다".
- 입력 32K·동시 32의 속도 비율.
- 10-03·10-04의 오염된 수치: 동시 128에서 812 tok/s, 출력 100만 토큰당 28.01·17.38달러, 2K~8K 입력에서 B200 대비 0.43~0.51배, "TP16이 짧은 입력에서 12~41% 빠르다", dense가 native보다 1.11~1.64배 빠르다는 비율, 단일 요청 첫 토큰 1.65초(8K)·7.21초(32K), "NVFP4가 동시 32까지 FP8과 같은 속도". 단일 요청의 TPOT는 디코드만 재므로 영향을 받지 않는다.
- 토큰당 비용, NVFP4와 FP8의 품질 동등성.
- "저우선순위 노드는 시간당 8.19달러". 저우선순위는 2026-03-31부터 Spot으로 할당·과금된다(증거 확인). 영국 남부 Spot 요금 기준 노드 2대는 시간당 약 25.78달러다.

## 7. A100에서 시도하지 않은 최적화

### 7.1 시험할 가치가 있는 것 (우선순위순)

1. **`--max-model-len`을 필요한 길이로 줄인다.** 근거는 A1이다. 동시 요청이 많을 때 디코드 단계당 수 ms를 줄일 수 있다(추정). 대가는 최대 컨텍스트 감소다. 플래그 1개로 시험한다.
2. **EP 전문가 배치를 `round_robin`으로 바꾼다.** 근거는 A8이다. EP 손해가 줄거나 뒤집힐 수 있다(추정). DP=1 구성에서 지원된다. 플래그 1개로 시험한다.
3. **NVFP4 TP8 독립 복제본 2개를 노드마다 1개씩 띄우고 외부에서 부하를 나눈다(D×2).** A와 같은 GPU 16장으로 직접 비교할 수 있다. DP 동기화 비용이 없다. NVFP4 품질 검증이 전제다.
4. **EPLB(중복 전문가로 부하 분산).** vLLM 문서는 DeepSeek-V3에서 랭크당 중복 전문가 1개에 약 2.4 GB가 든다고 한다. KV 용량과 맞바꿔야 한다.
5. **스케줄링·그래프 설정을 조정한다.** `--async-scheduling`을 명시하고, CUDA graph 캡처 크기와 구성별 `--max-num-batched-tokens`를 조정한다.
6. **포트 커널을 개선한다.** 분할 휴리스틱(A2), 인덱서 그리드 크기(A1의 근본 수정), 융합 RMSNorm(A5)이 대상이다. 코드 변경과 수치 검증이 필요하다.
7. **DCP(decode context parallel)로 TP16의 KV 복제를 줄인다.** 포팅된 SM80 백엔드에는 DCP 관련 코드가 없다. 지원하지 않을 가능성이 높다(미확인). 서버가 플래그를 받아들이는지만으로는 확인되지 않는다. DCP=1과 2의 KV 토큰 수, DCP 그룹 로그, 출력 동등성, 짧은 부하 결과를 비교해야 한다. KV가 늘지 않으면 지원하지 않는 것으로 본다.
8. **프리필과 디코드를 노드별로 나눈다(PD 분리).** NVFP4만 가능하다(프리필 노드 1대, 디코드 노드 1대). FP8은 모델이 노드 1대에 들어가지 않아 노드 4대 이상이 필요하다.

### 7.2 A100에서 불가능하거나 효과가 없는 것

- **DeepEP, DBO, DeepGEMM:** Hopper(SM90) 이상 전용이다(확인).
- **FP8 단일 노드 복제본:** FP8 가중치 694.4 GB가 노드당 GPU 메모리 640 GB보다 크다.
- **EAGLE3와 CUDA graph 병용:** TRITON_MLA 디코드는 요청당 쿼리 토큰 1개만 받는다(확인). 기존 EAGLE3 측정은 eager 모드라 비교가 공정하지 않다.
- **Marlin MoE 설정 파일 튜닝:** Marlin 경로는 Triton fused-MoE 설정 파일을 읽지 않는다(확인).

## 8. 고객 공유 수준 성능 검증 계획 (계획, 미실행)

이 절의 내용은 모두 계획이다. 아직 실행하지 않았다.

### 8.1 현재 충족도

고객이 서빙 권고를 믿기 위해 필요한 21개 항목을 현재 증거와 대조했다. 충족 3개, 부분 충족 10개, 누락 8개다.

- **충족:** 단일 요청 지연, 구성별 KV 용량과 최대 컨텍스트, 오류·타임아웃 집계.
- **누락:** 반복 실행과 신뢰구간, 지연-처리량 곡선, SLO 기준 goodput, 정상 상태 구간, 장시간 부하, P99 표본 수, GPU·IB 계측, 복제본 확장 검증.

항목별 판정과 추가 측정은 측정 방법 검토 보고서(저장소 밖)에 있다.

### 8.2 대표 구성

| 이름 | 구성 | GPU | 선정 이유 |
|---|---|---|---|
| A | FP8 TP8×PP2 | 16 | 현재 제안. FP8 중 단일 요청 지연이 가장 짧고 KV가 가장 크다. 최대 컨텍스트 262,144토큰 |
| C2 | FP8 DP2×TP8+EP16 | 16 | 동시 32에서 1K·8K·32K 세 입력 모두 A를 넘은 유일한 구성(1회 측정, 조건 혼재). 단일 요청 지연과 KV에서 손해를 본다. SLO 기준으로 판정해야 한다 |
| D | NVFP4 TP8 (노드 1대) | 8 | A와 단일 요청 지연이 비슷하고 GPU는 절반이다. 노드 1대 단위 결과와 D×2 확장 비율의 기준이 된다. 품질 동등성 검증이 필요하다 |
| A′ | A를 라운드 끝에 다시 실행 | 16 | 같은 라운드 안의 실행 간 잡음과 시간에 따른 변화를 통제한다 |
| D×2 (별도 1회) | NVFP4 TP8 독립 복제본 2개 + 부하 분산기 | 16 | 같은 GPU 16장에서 A와 비교한다. 품질 검증을 통과한 뒤 별도 작업으로 1회 검증한다. 실제 부하 분산기 없이 클라이언트에서 요청을 나누면 "부하 분산기 미검증 상한"으로 표시한다 |
| C2-s (1라운드 1회) | C2 + 엔진별 배치 한도 절반(4,096토큰, 64시퀀스), API 서버 수 고정 | 16 | 합계 한도를 A(8,192토큰, 128시퀀스)와 같게 맞춰, C2의 동시 처리 이득이 합계 한도 2배에서 오는지 분리한다 |

B, B0, C1, E는 제외한다. 이번 측정에서 A보다 나은 지표가 없었다. B0의 동시 32 1K·8K ×1.04는 잡음 범위로 본다. 단, round-robin 진단에서 EP 손해가 사라지면 EP 구성을 다시 포함한다.

성능 측정 단계에서는 모든 구성에 같은 `--max-model-len`을 고정한다. 값은 고객의 최대 입력 길이에 맞추고 C2의 상한 238,656 이하로 정한다(예: 131,072). 자동 맞춤(`-1`)을 쓰면 구성마다 실제 값이 달라져 A1 요인이 섞이기 때문이다. 최대 컨텍스트는 별도 용량 단계에서 `-1`로 잰다. 고객이 262,144토큰을 반드시 요구하면 C2는 후보에서 뺀다.

### 8.3 측정 내용

1. **출력 동등성:** 고정된 실제 텍스트 18개로 A 대비 토큰별 log-prob 차이를 잰다. 그리디 생성 32개 × 256토큰에서 처음 달라지는 위치를 기록한다. NVFP4는 KoBALT 200문항과 CLIcK 300문항으로 비열등성을 검정한다(허용 폭 −3점).
2. **기존 측정 재현:** 1K·8K·32K 단일 요청, 1K·8K 동시 32. 측정 지점마다 프리픽스 캐시를 비운다.
3. **개방형 도착 부하 곡선:** W1 채팅형(입력 1K, 출력 512토큰)과 W2 RAG형(입력 8K, 출력 512토큰)에 Poisson 도착률 4단계를 적용한다. 도착률 격자는 90% goodput 경계의 양쪽을 모두 포함해야 한다. 포함하지 못하면 그 측정은 무효로 보고 격자를 옮겨 다시 잰다. 1라운드 뒤 경계 주변으로 격자를 재조정한다. 격자 밖으로 외삽하지 않는다.
4. **SLO 기준 goodput:** 요청의 90% 이상이 TTFT와 TPOT 기준을 모두 지키는 최대 도착률(λ*)을 구한다.
5. **실제 텍스트 부하:** A와 C2에 실제 한국어·영어 텍스트(고객 데이터가 있으면 그것)로 W1을 λ* 근처 도착률 2개에서 잰다. 연속 난수 토큰과 실제 텍스트는 MoE 전문가 선택 분포가 달라 EP 성능이 다를 수 있다.
6. **장시간 부하:** λ*의 80%로 45분 동안 유지한다.
7. **계측:** vLLM `/metrics`를 1초 간격으로 엔진별로 저장한다(선점, 캐시 적중 포함). 스텝별 스케줄 토큰 수와 CUDA graph 모드를 기록한다(A의 PP 마이크로배치 확인용). nvidia-smi로 클럭·전력·온도·스로틀 원인을 기록하고, InfiniBand 포트 카운터를 측정 전후에 읽는다.
8. **비용:** λ*에서 출력 100만 토큰당 비용과 신뢰구간을 낸다. 가격은 발표일에 Azure 소매가를 다시 조회한다.

SLO 기본안은 다음과 같다. 이 값은 가정이다. 고객 기준이 있으면 그것을 쓴다.

| 워크로드 | 기준 SLO (P90) | 엄격 SLO (P90) |
|---|---|---|
| W1 채팅형 1K/512 | TTFT ≤ 3초, TPOT ≤ 100 ms | TTFT ≤ 1초, TPOT ≤ 50 ms |
| W2 RAG형 8K/512 | TTFT ≤ 6초, TPOT ≤ 100 ms | TTFT ≤ 3초, TPOT ≤ 50 ms |

### 8.4 통계와 판정 규칙

- 3라운드로 시작한다. 라운드마다 별도 작업으로 실행하고, 최소 2개의 서로 다른 노드 할당을 쓴다.
- A·A′ 로그비의 라운드 간 표준편차가 2%를 넘거나, 주요 지표의 95% 신뢰구간 반폭이 5%를 넘으면 4~5라운드로 늘린다. 이 기준은 첫 라운드 전에 정한다.
- 라운드 안의 순서는 A → C2와 D(무작위 순서) → A′다.
- 같은 라운드에서는 모든 구성에 같은 프롬프트(같은 시드)를 쓴다. 측정 지점마다 시드를 다르게 하고 프리픽스 캐시를 비운다.
- A′는 시작, 워밍업, 기존 측정 재현, W1 도착률 2개만 실행한다. 따라서 A·A′ 평균으로 시간 변화를 보정하는 것은 이 겹치는 지표에만 적용한다. W2의 λ*와 비용은 A 단독 값을 기준으로 하고, 이 제한을 사전 등록 문서에 적는다.
- "X가 A보다 낫다"고 말하려면 세 조건을 모두 만족해야 한다.
  1. 모든 라운드에서 X가 앞선다.
  2. 95% 신뢰구간이 1을 포함하지 않는다.
  3. 효과가 5%와 A·A′ 차이의 2배 중 큰 값 이상이다.
- 95% 신뢰구간 전체가 [0.95, 1.05] 안에 있으면 "동등"이라고 쓴다. 나머지는 "판정 불가"와 신뢰구간을 쓴다.
- P99는 정상 상태 구간의 요청이 1,000개 이상일 때만 보고한다.
- 첫 라운드 전에 SLO, 도착률, 시드, 판정 규칙, 분석 스크립트를 커밋으로 고정한다. 무효 실행도 모두 공개한다.

## 9. 결정이 필요한 사항

1. **SLO와 워크로드:** 고객 기준을 쓸지, 8.3의 기본안으로 시작할지 정한다.
2. **대표 구성:** A, C2, D, A′와 별도 검증 D×2, C2-s로 확정할지 정한다.
3. **공통 컨텍스트 상한:** 성능 측정에 쓸 `--max-model-len`(예: 131,072)을 고객의 최대 입력 길이에 맞춰 정한다.
4. **GPU 예산:** 진단 실험(Spot 약 52달러)을 먼저 승인하고, 그 결과를 보고 최소안(Spot 약 705달러)을 승인할지 정한다.
5. **문서·발표 자료 수정:** 6절 오류는 이 보고서와 같은 변경에서 고쳤다(10절). 고객에게 공유하기 전에 정정본을 다시 확인한다.
6. **버그 수정 반영:** 수정한 포트는 이 변경에 들어 있다. 고객용 재측정은 GPU 회귀 시험을 통과한 수정 포트로 할 것을 권고한다. 이전 실행과 코드가 달라지므로 그 사실을 기록한다.
